Sequence

Do the phases in this order. The reasons are dependencies, not preference.

  1. Stability. Phase 2 moves code that user projects depend on. Do not move it while an error is permanent.
  2. Four tabs. Project, Data, Triggers and Resources. The editor follows the subject, not the file format.
  3. Trigger foundations. A format with a schema, a model with types, and a generator that reads the model.
  4. Modern EUD. Typed game objects, loops over units, collections and formatted text. Nine items. This is the reason for phase 3.
  5. Tools and quality. Search, validation and a difference view. Each one is simple after phase 3.

Phase 1

Stability

The editor must not lose user data. Complete this phase before you move code.

01

Undo and redo in the data editorsDone

Problem
DatEdit, FireGraft and the string table have no undo. A wrong keystroke writes a value. The user cannot go back.
Solution
Add one command log for the data editors. Most edits use two write methods on one data class. Connect the log to those two methods. Refresh the list and the fields after an undo. Scope the history to the tab, not to the editor. The trigger editor keeps its own, because it records only about half of its changes, and a merged stack would undo the wrong thing in a tab the user is not looking at.
Result
One history for each main tab. DatEdit, FireGraft, FileManager and the string table record their edits. An undo opens the data type and the entry that the edit changed, and marks the field for a moment.
Effort 1 weekArea DatEdit
02

Autosave and crash recoveryDone

Problem
A crash discards all changes after the last manual save. The crash log has no reader.
Solution
Write a recovery copy of the project every 5 minutes. Offer the copy at the next start. Show a crash dialog with the cause and a copy button.
Result
The editor writes a recovery copy every five minutes while there are changes that are not saved, and after an error. A save or a close takes the copy away, so a copy that is still there at the next start means the editor stopped without a save; the editor then offers it. An error window gives the cause, the place of the copy, and a button that copies the details.
Effort 2 daysArea Project data
03

Correct the error handlingIn part

Problem
Empty catch blocks hide failures. A file that does not load looks the same as an empty file. Some catch blocks replace a missing bounds test and run on a hot path.
Solution
Replace each catch block with the correct test where the intention is clear. Record the other errors. Also remove the references that construct a form as a side effect. One such reference built the FireGraft window during each DatEdit load.
Result
Every catch block that said nothing now reports, one time for each place, so a hot path cannot fill the log. That is 225 places. The first run of the editor reported six faults that nobody could see before, and each is now corrected: a menu separator that the language code treated as a menu item; three reads outside the range of a list; a value that is a name where a number was expected; and a list of flags whose write was thrown away in full, so a change to a unit flag did nothing. Two caches were also filled under one name and read under another, so they never answered. Still to do: the catch blocks that hide a fault only under conditions this run did not meet.
Effort continuousRisk correctness
04

Reference build

Problem
No test shows whether a code change alters the generated output.
Solution
Compile a set of reference projects. Keep the generated files. Compare the files after each change. Identical output proves the change is safe.
Effort 2 daysRequired for phase 3
Phase 2

Four tabs, by subject

The editor has a window for each file format. A unit's data is in four of them. Replace that with four tabs named after the subject: Project, Data, Triggers and Resources. Each old editor becomes a pane inside the tab it belongs to, and keeps its controls.

Do the move first and the merge second. Item 05 changes where a screen lives. Items 06 to 08 change how the screens inside a tab work together. A user can follow the first step without relearning anything.

05

Four tabs, by subjectDone

Problem
The editor has one tab for each file format. A user who wants to change a unit opens DatEdit for the values, FireGraft for the requirements and the button set, and FileManager for the wireframe and the name. The structure follows the data, not the work.
Solution
Group the editors into four tabs: Project, Data, Triggers and Resources. Each old editor becomes a pane inside its tab, with its controls unchanged. A user who knows the editor finds the same screens, in fewer places. Each tab carries its own Edit menu and its own undo history, so Ctrl+Z always means "undo my last change in this tab".
Result
Project, Data, Triggers and Resources, each with an Edit menu and a history of its own. The editors load without a first paint. TileSet, GRP and BinEditor are hidden, because they are unused.
Effort 2 weeksArea Shell
06

The Data tab, by conceptIn part

Problem
DatEdit has one inner tab per .dat file. FireGraft is a separate window with the requirements and the button set of the same units. The user holds the connection in their head.
Solution
Give the Data tab one list per concept: units, weapons, upgrades, techs, orders, graphics, sounds. Select a unit and see its values, its requirements, its button set and its wireframe on one page. The .dat files stay as they are; only the presentation changes.
Result
DatEdit is the only view under Data. FireGraft has no pane: its fields are sub tabs of the data type they belong to, and its button sets are the eleventh kind of data. A tab carries the number of the kind of data it shows, so an unsupported page can go; Portrait is gone for that reason. Still to do: the wireframe and the name, which FileManager holds.
Effort 3 weeksNeeds 05
07

The Resources tab

Problem
The map archive, the graphics, the string table and the sounds each have a window, and several have more than one. The user cannot answer "what is in this map" from one place.
Solution
Put the archive browser, the graphics, the strings and the sounds in one tab with a type filter and a preview. All of these windows already call the same archive reader, and the archive listing is cached.
Effort 2 weeksNeeds 05
08

The Project tab, and one build actionIn part

Problem
Plugins are a separate tab although they are project configuration. There are five ways to build the mod into a map and three ways to read the generated code.
Solution
Move the plugin list into the Project tab beside the other project settings. Reduce the build to one action with options, and the output to one panel with tabs for the script, the triggers and the log.
Result
Project settings, plugins and files are sub tabs of Project. The build log is a dock at the foot of the main window, which the user can hide, resize or pop out. A save builds the map. Still to do: one build action, and one panel for the generated code.
Effort 1 weekNeeds 05
09

Inline value pickers

Problem
The trigger editor opens a modal dialog to select a unit, a player, a switch, a wait or a string. The user must close the dialog before the user can see the trigger.
Solution
Make one inline picker. The picker reads the type of the field. Each list is already in memory.
Effort 2 weeksArea Triggers
Phase 3

Trigger system foundations

The format, the model and the generator. Each layer can ship separately. Item 04 verifies each change.

These four items do not add a function for the user. They make phase 4 possible.

10

Function file format

Problem
The 56 function files use a private format. The format has numeric type codes, an element count before each child, an END marker, and one Tamil letter as the field separator. The help text for each language is inside each node. A change is not readable in a diff. A new language needs an edit to all 56 files.
Solution
Use JSON with a schema. Convert the files one time. Move the help text to the language files. Validate each file at load.
Effort 1 to 2 weeksNeeds 04
11

Trigger model

Problem
The trigger tree is the data and the interface. Each node holds its own display text. The generator reads the tree control. Search, test and validation need an open window. The model has 30 node types: if, while, for, switch, function, action, condition, folder and raw code. It has no type for a value.
Solution
Make a model that does not depend on a window. Give a value a type: a number, a unit, a player, a unit pointer, an array. The tree control shows the model. This item enables all of phase 4.
Effort 3 to 4 weeksRisk high
12

Generator

Problem
The generator concatenates strings across a module of 1,393 lines. It decides the format at each site. The output is not testable.
Solution
Generate epScript from the model. Keep the source position of each node. A compile error then points to the trigger.
Effort 2 weeksNeeds 11, 04
13

Compiler version check

Problem
The editor does not know which euddraft version is installed. It does not know which functions that version accepts. A build finds the error.
Solution
Read the version at start and show it in the status bar. Keep a table of the version of each function. Warn before the build.
Effort 3 daysArea Build
Phase 4

Modern EUD, natively

This is the transformation. Everything before it is preparation.

The trigger editor gives the user conditions, actions, variables and raw memory. epScript and eudplib give the user typed game objects, loops over units, collections and formatted text. A user who wants the second set leaves the editor, or pastes an address into a memory action and hopes. 

// To add 3 damage to a weapon, a user writes this today.
const offset = 0x656EB0 + EncodeWeapon("Fragmentation Grenade") * 2;
wwrite(offset, wread(offset) + 3);

// epScript has had this since the SCData release.
TrgUnit("Terran Vulture").groundWeapon.damage += 3;

The 56 built-in trigger functions are the evidence. Each one wraps an address and a size that somebody looked up once, and each one is a copy that nobody can check. Give the user the concept instead of the wrapper.

One rule for this phase: the editor does not become a text editor. The tree keeps its place. It gets the vocabulary that the language already has. Item 22 is the door for users who prefer text.

14

Named game data in a trigger

Problem
The .dat values the Data tab edits are fixed when the map is built. To change one while the map runs, a user writes a memory address and a byte size. The address 0x656EB0 does not say "weapon damage". The multiplication by 2 does not say "each weapon record is 2 bytes long".
Solution
Add a data action and a data condition with named fields. The user picks the subject, then the field, then the operation: set, add, subtract. The generator emits the member access and eudplib computes the address and the size. The same field names the Data tab shows before the build become available during the game.
// action: Terran Vulture, ground weapon, damage, add 3
TrgUnit("Terran Vulture").groundWeapon.damage += 3;
// condition: max hit points of Terran Marine is at least 60
TrgUnit("Terran Marine").maxHp >= 60 * 256

Covers Units with 40 fields, weapons with 16, upgrades with 12, techs with 10, orders with 11, flingy, sprites, images, and the resources and supply of a player. A field that holds another kind of data returns that kind, so the user can walk from a unit to its weapon to that weapon’s damage in one expression.

Effort 2 weeksNeeds 11
15

Live units as a value

Problem
A trigger cannot read the units that exist in the running game. To read the hit points of a unit, a user finds the offset 0x08 in the EUD offset book, divides an address by four, and writes a memory condition. The unit structure has about 190 named fields. The editor exposes none of them.
Solution
Add a unit pointer value type. A user selects a field by name and reads or writes it like a variable. The fields are typed, so the target of an order is another unit, the owner is a player, and the unit type is game data. The user can therefore follow a chain: the owner of the target of this unit’s order.
// give 100 minerals to the owner of the unit this unit is attacking
unit.orderTarget.owner.ore += 100;
// raise the maximum hit points of this unit’s type
unit.unitType.maxHp += 20 * 256;

Covers Position, hit points, shield, energy, owner, unit type, order and order target, both weapon cooldowns, build queue, resource amount, transport contents, hangar contents, and the timers for stim, ensnare, lockdown, irradiate, stasis, plague and storm. Sprites carry the graphic.

Effort 3 weeksNeeds 11
16

Named state flags

Problem
A unit carries 33 state flags in three groups. A user who wants to know whether a unit is cloaked writes a bit mask as a number. The number does not say "cloaked". A user who sets the wrong bit gets no error, only a map that behaves strangely.
Solution
Show the flags as a named list with check boxes. Read them in a condition and set them in an action. Group them as the game does: state, movement and pathing.

Covers Completed, In air, Burrowed, In transport, In building, Cloaked, Requires detection, Invincible, Hallucination, Holding position, Can not attack, Can not receive orders, Is gathering, Speed upgrade, Cooldown upgrade, Has collision, Is stacked, and 16 more.

Effort 4 daysNeeds 15
17

Loops over the objects of the game

Problem
The trigger model has while, for and switch. It has no loop over the objects of the game. To act on each unit of a player, a user writes a function with a counter and a memory read, or copies one of the 56 built-in functions and changes it.
Solution
Add a foreach block. The user picks the source. The block gives a unit value that the rest of the phase can use. Each source is a loop eudplib already provides, so the generated code is the one the library authors optimised.
// for each unit created since the last run
foreach(unit : EUDLoopNewCUnit()) {
    // the tree of this block goes here
}

Covers All units, units created since the last run, the units of one player, all players, bullets and sprites.

Effort 1 weekNeeds 11, 15
18

Unit groups

Problem
To act on a set of units across several game ticks, a user builds an array of addresses and manages the indices. To notice that a member died, the user compares each entry every tick and removes the entry by hand. This is the most common source of a slow map.
Solution
Add a unit group value. The user adds a unit to it, loops over it, and handles a dying member in a block inside that loop. The library removes the dead member at the end of that block.
// spawn an Infested Terran where a tracked Zergling dies
foreach(unit : zerglings.cploop) {
    foreach(dead : unit.dying) {
        // the position and owner of the dead unit are available here
    }
}
Effort 1 weekNeeds 15, 17
19

Collections

Problem
The trigger editor has flat variables. A user who needs a table of values declares many variables and keeps the meaning of each index in their head. A user who needs a waiting list writes the list logic from the start each time.
Solution
Add an array value with an index, and the three collections that follow from it: a queue, a stack and a pool of reusable objects. Each one is a type in the library already.

Covers Array by index, array of structures, queue with append and take, stack with push and pop, and an object pool with allocate and free for a fixed number of reusable records.

Effort 2 weeksNeeds 11
20

Structures and functions with types

Problem
A trigger function takes numbers. A user who passes a unit type to a function passes a number and remembers what it means. There is no way to group related values under one name.
Solution
Add a structure with named fields, and give a function parameter a type. The editor can then check the argument before the build, and offer the fields of the value the user selected.
// a typed parameter, checked before the build
function makeStronger(unitID: TrgUnit) {
    unitID.maxHp += 20 * 256;
}
Effort 2 weeksNeeds 11, 19
21

Text with arguments

Problem
Text output joins strings by hand. A colour is an escape character typed into the string. A number is converted and concatenated. The user cannot see the result before the build.
Solution
Add one text action with a format string, arguments, a colour picker and a preview. Add the text buffer for text that the map changes as it runs, such as a score board or a chat log.
// print with an argument, to every player
printAll("\x04Player 7 gas: {}", P7.gas);

Covers Print to all players, print at a position, a text buffer with append, insert and delete, a fade effect, and the Korean and UTF-8 encodings the game accepts.

Effort 1 weekNeeds 11
22

epScript beside the tree

Problem
The tree and epScript are separate worlds. A user who knows epScript cannot read what the tree produces. A user who has an epScript file cannot bring it into the editor. The two groups of users cannot read each other’s work.
Solution
Show the epScript of the selected trigger beside the tree. Let the user edit it there and read the result back into the model. The user then uses the tree for structure and the text for detail. This also gives the editor a way to accept the code that the community already publishes.
Effort 3 weeksNeeds 11, 12
Phase 5

Tools and quality

Each item is expensive today and simple after phase 3. Item 25 has no dependency and can start at any time.

23

Find all references

Problem
To find where a trigger sets a switch, the user reads the generated script.
Solution
Query the model. Show each use. Add a safe rename function.
Effort 4 daysNeeds 11
24

Validation during the edit

Problem
euddraft reports a wrong argument count or an unknown variable minutes later. The message gives a line number in the generated file.
Solution
Validate the model after each change. Mark the incorrect trigger in the tree. The schema from item 10 defines a correct argument.
Effort 1 weekNeeds 11, 10
25

Difference against the stock game data

Problem
The project keeps user edits separate from the stock game data. The editor knows each difference. It does not show them.
Solution
List each changed value with its original value and a revert button. Group the list by data file. The list is also the changelog for a release.
Effort 1 weekNeeds nothing
26

Edit multiple entries

Problem
A balance change for one race is one unit at a time.
Solution
Select a range in the list. Set one field for all selected entries.
Effort 4 daysNeeds 01
27

Field documentation

Problem
The field descriptions are on external sites. The Help menu has the links. The user leaves the editor to read them.
Solution
Show the description of a field in a tooltip. The code is one day. The content is several hundred descriptions. The community can supply them.
Effort openArea Documentation

Start with items 01 and 04. Item 01 makes an error reversible before phase 2 moves code. Item 04 proves that phase 3 does not change the output.

Phase 3 is not the goal. It is the cost of phase 4. Read items 14 to 22 first, then decide how much of phase 3 you need.

Do not change the UI framework. WinForms is not the limit. One form with 587 controls is slow in each framework that gives a window to each control.

Sources for phase 4: the euddraft wiki, the eudplib source and the EUD offset book. The Help menu links all three.
